# 設計提案書（実装前レビュー用）

本書は「ゲーム企画・要件概要」を受けて、技術構成・MVP範囲・開発方針を提案するものです。
実装はまだ行っていません。末尾の「確認したい事項」へのご回答をもって第1段階（MVP）の実装に入る想定です。

---

## 1. 要件の整理

| 区分 | 要件 | 段階 |
|---|---|---|
| 必須(MVP) | ブラウザで起動 / 手動運転（アクセル・ブレーキ・ハンドル） / 小さなマップ / 障害物で停止 / 三人称視点 / 速度表示 | 第1段階 |
| 改善 | 車内視点（運転席）、前輪の舵角・タイヤ回転、マップ拡充、衝突挙動の改善 | 第2段階 |
| 特徴機能 | キャラクターの自動運転、音声指示、リアクション・字幕、助手席視点 | 第3段階 |
| 拡張 | オンライン（2〜5人）、フリードライブ、レース、共同運転 | 第4段階 |

要件から読み取れる**設計上の最重要ポイント**は次の3つです。

1. **車両挙動を「手動」「キャラクター」「他プレイヤー」で共通化する**
   → 車は常に `{ throttle, brake, steer }` という同じ入力で動かし、入力の出どころ（キーボード / AI / ネットワーク）だけを差し替える。
2. **「次の交差点を右」を理解するには、マップが“道路のつながり”を知っている必要がある**
   → マップを見た目のメッシュではなく、**道路グラフを持つデータ**として定義する。
3. **オンライン化を後から足せるようにする**
   → シミュレーション（物理・ゲーム状態）と描画を分離し、車の状態をシリアライズ可能に保つ。

この3点は MVP の時点から構造として仕込みます（機能は作り込みません）。

## 2. 技術構成（推奨）

| 領域 | 推奨 | 理由 |
|---|---|---|
| 言語 | **TypeScript** | 規模が大きくなっても破綻しにくい。ブラウザで完結 |
| ビルド | **Vite** | 設定がほぼ不要、起動・HMRが高速 |
| 3D描画 | **Three.js** | 最も情報量が多いWeb 3Dライブラリ。軽量で自由度が高い |
| 物理・衝突 | **Rapier**（`@dimforge/rapier3d`, WASM を別ファイルで配信） | 高速・無料・CCD（すり抜け防止）対応。将来の車同士の衝突、障害物を押す動作もそのまま扱える |
| UI | 素のHTML/CSSオーバーレイ | 速度計・字幕程度ならフレームワーク不要 |
| テスト | **Vitest** | 車両モデル・AI・指示解析など描画に依存しないロジックを単体テスト |
| ホスティング | **GitHub Pages**（または Cloudflare Pages） | 静的サイトなので無料。GitHub Actionsで自動デプロイ |

### 検討した他の選択肢

- **Babylon.js**：物理・エディタ込みで高機能だが、Three.jsより重く情報も少なめ。Three.jsでも十分。
- **React Three Fiber**：宣言的で便利だが、ゲームループ主体のコードでは抽象化が一枚増える。個人開発のシンプルさを優先して見送り。
- **Unity / Godot のWeb書き出し**：エディタは強力だが、ビルドサイズ・起動時間が大きく、Web Speech APIやWebRTCなどブラウザAPIとの連携が面倒。「ブラウザ向け・シンプル構成」の方針に合わないため不採用。

## 3. アーキテクチャ

```
入力ソース ──► DriverInput {throttle, brake, steer} ──► 車両シミュレーション ──► 描画
 ├ キーボード/ゲームパッド（手動）                         （Rapier + 独自タイヤモデル）   （Three.js）
 ├ キャラクターAI（第3段階）                                        │
 └ ネットワーク（第4段階）                                          └► 車の状態 {位置, 向き, 速度, 舵角}
                                                                            → カメラ / HUD / 同期
```

### ディレクトリ構成案

```
src/
  main.ts            起動処理
  core/              ゲームループ（固定タイムステップ）、入力
  sim/               車両モデル・物理ワールド（Three.jsに依存しない）
  map/               マップ定義データ、マップ生成、道路グラフ
  render/            シーン、車モデル、カメラ
  ui/                HUD（速度・モード・字幕）
  ai/                キャラクター運転（第3段階）
  voice/             音声認識・指示解析・返答（第3段階）
  net/               オンライン同期（第4段階）
```

### ゲームループ

- 物理は **固定 60Hz** で更新、描画はディスプレイのリフレッシュレートで補間表示。
- 固定ステップにすることで、フレームレートに関係なく挙動が一定になり、テスト・オンライン同期もしやすくなる。

## 4. 車両挙動の実現方法

### 方針：「剛体 + 独自のアーケード寄りタイヤモデル」

車体は Rapier の**動的剛体（箱型コライダー）**とし、毎ステップ自前で次の力を加えます。

1. **駆動・制動**：アクセルで前方向に力、ブレーキ／後退、空気抵抗・転がり抵抗で自然減速。
2. **旋回**：自転車モデル（前後輪を1本ずつとみなす簡易モデル）で、舵角と速度から旋回量を決める。
   - 低速では小回り、高速では舵角を自動的に絞って曲がりすぎないようにする（＝「速度で曲がり方が変わる」）。
3. **グリップ**：横滑り速度を減衰させてタイヤのグリップを表現（値を下げればドリフト気味にもできる）。
4. **ハンドル**：入力に対して舵角が滑らかに追従し、離すと中央へ戻るセルフアライニングを入れる。
5. **姿勢**：横転防止のため X/Z 軸回転は固定（MVP）。坂道が必要になったら緩める。

### この方式を選ぶ理由

| 方式 | 長所 | 短所 |
|---|---|---|
| 完全自前（運動学のみ） | 単純・決定的 | 衝突応答・押し合いを全部自作する必要がある |
| Rapier の Raycast Vehicle（サスペンション付き） | リアル | パラメータ調整が難しく、不安定になりやすい |
| **剛体 + 独自タイヤモデル（推奨）** | 操作感を自分で調整でき、衝突・押し合いは物理エンジンが担当 | 本格シミュレーターほどリアルではない（要件上問題なし） |

衝突は物理エンジンが解決するため「壁にぶつかったらすり抜けずに止まる」が自然に満たされ、将来の車同士の衝突やコーンを押す動作も追加実装なしで動きます。
パラメータ（最高速、加速、最大舵角、グリップなど）は1つの設定オブジェクトにまとめ、将来の車種追加はパラメータ差し替えで対応します。

## 5. マップ・コース

### 方針：タイルベースのデータ駆動マップ

マップは **グリッド上に道路タイルを並べたデータ**（TypeScript/JSON）として定義し、そこから3Dメッシュ・衝突体・道路グラフを自動生成します。

```ts
// イメージ
const map = {
  tileSize: 20,
  tiles: [
    "┌──┬──┐",
    "│  │  │",
    "├──┼──┤",
    "│  B  │",   // B = 建物
    "└──┴──┘",
  ],
};
```

- タイル種別：直線、カーブ（左右）、T字路、十字路、建物、空き地 など。
- 道路外周にはガードレール／縁石、建物は箱型コライダー。
- **道路グラフ**（交差点＝ノード、道路＝エッジ）もタイルから自動生成 → 第3段階のAIが「次の交差点」を判断する基盤になる。
- 新しいマップ（教習所・街・サーキット・峠）はデータを書き足すだけで追加できる。峠道のような自由形状が必要になった段階で、スプライン道路の生成を追加検討する。

### 3Dアセット

- **MVPは Three.js の基本図形（箱・円柱）で車・建物を表現**し、外部アセットに依存しない。
- 第2段階で見た目を改善する際は **Kenney の Car Kit / City Kit 等（CC0：クレジット不要・商用可）** を第一候補とする。
- 外部アセットを導入する場合は `assets/LICENSES.md` に出典とライセンスを記録する運用にする。

## 7. キャラクターによる運転（第3段階・設計のみ）

キャラクターは**手動運転と同じ `DriverInput` を出力するAI**として作ります。

1. **経路計画**：道路グラフ上で「今いる道路 → 次の交差点 → 指示された方向」を決める。
2. **経路追従**：Pure Pursuit（前方の目標点に向けて舵を切る定番手法）で舵角を、速度は目標速度へのP制御でアクセル/ブレーキを決める。
3. **指示ステートマシン**：`停止中 / 発進 / 巡航 / 減速 / 右左折予約 / 緊急停止` などの状態を指示で遷移。
4. **障害物回避**：前方レイキャストで障害物・他車を検知して減速・停止。
5. **“運転が苦手”演出**：以下をパラメータ化し、難易度として調整可能にする。
   - 反応遅延（指示から操作までの時間）、ハンドルの切り遅れ・切りすぎ
   - 一定確率の急ブレーキ、曲がる方向の間違い、聞き間違い
   - **理不尽さを避けるため**、緊急停止系は遅延を小さく・失敗確率をゼロにするなど、指示の種類ごとに失敗率を設定する。

## 8. 音声認識・指示理解（第3段階・設計のみ）

### 初期版：Web Speech API ＋ キーワード辞書

- ブラウザ標準の **Web Speech API（SpeechRecognition）** を使用。無料・日本語対応・実装が容易。
- 認識結果を**決まった指示パターン（辞書・正規表現）**に照合して、`ACCELERATE / SLOW_DOWN / STOP / TURN_RIGHT_NEXT / CANCEL_AND_TURN_LEFT / DANGER ...` などの「指示」に変換する。
- **緊急指示の速さ**：確定結果を待たず**途中結果（interim）**で「止まって」「危ない」「ストップ」を検出した時点で即実行する。
- 認識した文と解釈結果は画面に表示する。

注意点：

- Chrome / Edge では動作するが、**Firefox は非対応**、Safari は不安定。音声はブラウザ提供元（Google等）のサーバーで処理される。
- そのため、**同じ指示をキーボード・画面ボタンでも出せる**ようにし、音声が使えない環境でも遊べるようにする（デバッグにも有用）。

### 将来の拡張候補

- 自由な言い回しへの対応：LLM API で「発話 → 指示JSON」に変換（ただし有料・遅延あり。緊急指示は辞書側で即処理し、LLMは複雑な指示のみに使う二段構え）。
- オフライン・ブラウザ非依存化：Vosk や Whisper の WebAssembly 版。

### キャラクターの返答

- 初期版：**字幕＋あらかじめ用意したセリフのランダム選択**。音声は Web Speech API の音声合成（無料）か、後から録音・合成音声ファイルに差し替え。
- 返答の種類（了解・驚き・失敗・雑談）をイベントに紐づけたセリフ表で管理する。

## 9. オンラインマルチプレイ（第4段階）

### 同期方式

- 各プレイヤーは**自分の車を自分のブラウザでシミュレーション**し、状態（位置・向き・速度・舵角）を 15〜20Hz で送信。
- 他プレイヤーの車は受信した状態を**補間（少し過去を表示）＋短時間の外挿**で滑らかに表示。
- 2〜5人・カジュアル用途ではこの「クライアント権威」方式が最もシンプルで、無料枠のインフラでも十分。チート対策は対象外とする。
- 車同士の衝突は、相手車を運動学的な剛体として自分の物理ワールドに置く方式から始める。

### 通信基盤の候補

| 候補 | 費用 | 特徴 |
|---|---|---|
| **Cloudflare Workers + Durable Objects（WebSocket）** | 無料枠あり | ルーム単位の中継サーバーをサーバーレスで運用できる。推奨 |
| WebRTC P2P（PeerJS 等） | ほぼ無料 | サーバー不要だが、NAT越えや接続の安定性に難あり |
| Node.js + Colyseus 等を常時稼働 | 無料枠は制約が多い | 機能豊富だが運用負担が増える |

**決定: クライアント権威 + Cloudflare Workers + Durable Objects（WebSocket Hibernation、SQLite 版で無料プラン）**。
実装では、部屋コード（4文字）ごとに1つの Durable Object が中継し、送信は 20Hz、表示は 100ms 遅れの補間＋最大 300ms の外挿。
マップは部屋で共有（最初に入った人のマップ、誰かが切り替えると全員が切り替わる）。
**MVPの段階でやっておくこと**は「車の状態をシリアライズ可能にする」「入力ソースを差し替え可能にする」の2点のみで、ネットワークコードは書きません。

## 10. 開発フェーズと実装順序

### 第1段階（MVP）— 実装する内容

1. プロジェクト雛形（Vite + TypeScript + Three.js + Rapier + Vitest）、GitHub Pages 自動デプロイ
2. 固定タイムステップのゲームループ
3. キーボード入力（`W/↑` アクセル、`S/↓` ブレーキ・後退、`A/D/←/→` ハンドル、`R` リセット、`C` カメラ）
4. タイルマップ1枚（直線・十字路・T字路・左右カーブ・建物・外周の壁・コーン数個）
5. 車両シミュレーション（第4章の方式）と、箱を組み合わせた簡易車モデル（前輪の舵角・タイヤ回転も表示）
6. 三人称追従カメラ
7. HUD：速度（km/h）、操作説明
8. 車両モデルの単体テスト（加速・停止・旋回・ハンドル戻りの基本特性）

**MVPの完了条件**：PCブラウザでURLを開くだけで遊べ、マップを一周走行でき、壁や建物に当たるとすり抜けずに止まること。

### 第2段階以降

- 第2段階：運転席視点、操作感の調整、マップ拡充（教習所コース等）、Kenney アセット導入、ゲームパッド対応、効果音
- 第3段階：キャラクターAI → ボタンによる指示 → 音声認識 → 返答・字幕 → 助手席視点 → 苦手演出
  （音声より先にボタン指示でAIを完成させ、音声は入力手段の追加として載せる）
- 第4段階：ルーム作成・参加 → 位置同期でフリードライブ → レース（チェックポイント・タイム・順位） → 共同運転

## 11. 確認したい事項

実装開始前に、以下についてご意見をいただけると助かります（特に指定がなければ推奨案で進めます）。

1. **技術スタック**：Three.js + TypeScript + Vite + Rapier で進めてよいか。
2. **車両挙動**：「剛体＋アーケード寄りの独自タイヤモデル」（操作の楽しさ優先）でよいか。
3. **音声認識**：初期版を Web Speech API（Chrome/Edge 前提、音声はクラウド処理）とすることに問題はないか。
4. **公開方法**：GitHub Pages でリポジトリから自動公開してよいか（リポジトリが非公開の場合、無料プランでは Pages を使えないため Cloudflare Pages を使う）。
5. **キャラクター設定**：「妹」に相当するキャラクター像（名前・口調など）は第3段階までに決める想定でよいか。
